**D8.1 — behaviour preserved, with one ordering change.** ARP and SYN now send due
retransmissions before never-sent probes, earliest first, where they interleaved in
address order. That is the ICMP sweep's existing policy. What is sent and the deadlines it
is armed with are unchanged.

**D8.2 — why a heap and not the timing wheel `02-the-cli.md` cites.** Deadlines here are
continuous instants from adaptive budgets, not ticks, and a wheel needs a resolution
chosen up front. At the sizes that matter (≤ 200k) log n is under 18. The heap is
simpler, and the test pins the bound.

**D8.3 — G8 as a comparison count, not a timing.** A wall-clock benchmark is a flaky
test on a shared CI runner. Counting comparisons is deterministic and is what the claim
is actually about.

## 2026-10-15 — G0: the routing socket says nothing when ARP resolves; change 1 polls (Claude)

**Question (brief, G0):** does a `PF_ROUTE` socket on macOS 26 deliver a message when an ARP
entry resolves, to an unprivileged process? **Answer: no.** Change 1 therefore re-reads the
table on a timer, and `run.neighbor_watch.mechanism` says `poll`.

The spike is `Docs/process/0.8.0-spike-route-socket.swift` (args: seconds to listen, the
socket's protocol filter, and an optional address to send an `RTM_GET` for, which proves the
socket is live). Compiled with `swiftc -O` and run as uid 501 / euid 501. The machine was on
10.10.40.0/24 (`en0` 10.10.40.19, gateway .1) — not the study LAN, which does not matter here:
this measures the kernel, not a scan.

**Run 1** — protocol filter `AF_INET`, 8 s, `ping -c1 -t1` to .2–.40. Eleven entries went
from absent to complete during the window (.4 .5 .6 .7 .8 .10 .11 .12 .13 .15 .16, from
`arp -an` before and after):

```
socket(PF_ROUTE, SOCK_RAW, AF_INET) = 3, uid 501, euid 501
0 message(s) in 8 s
```

Zero messages is also what a dead socket would show, so runs 2–4 used protocol 0 and an
`RTM_GET` to prove the socket delivers. Runs 2 and 3 resolved nothing new (the eleven were
still cached), so they prove only that the socket is live. **Run 4 is the valid one**: after
waiting for the eleven entries to expire (`net.link.ether.inet.max_age` 1200 s; at 13:51
only `.1` and this host's own `.19` were complete), protocol 0, `RTM_GET` for .1, 10 s,
`ping -c1 -t1` to .2–.40. The same eleven entries resolved again (`arp -an` after the run
lists all eleven complete, before it listed only .1 and .19). The socket delivered:

The `RTM_MISS` messages are a route lookup for `2001:4860:4860::8888` (an `AF_INET6`
sockaddr, bytes `1c 1e … 20 01 48 60 48 60 … 88 88`) every ~2 s from something else on the

llinfo route internally and announces it to nobody.

**What polling costs**, measured with an unprivileged `sysctl(CTL_NET, PF_ROUTE, 0, AF_INET,
NET_RT_FLAGS, RTF_LLINFO)` loop on the same machine, with the table holding 256 entries (240
of them incomplete, after a sweep of the /24): **36,860 bytes per read, 143 B per entry;
median 94.5 µs, p90 109.8 µs, max 227.5 µs per read.** Extrapolated to a /16 sweep (~65k
entries): ~9.4 MB and ~25 ms per read. Hence the interval in `NeighborWatch.interval(targets:)`:
25 ms up to 1,024 targets, then proportional, so a /16 reads every 1.6 s and the bytes copied
per second stay at what a /22 costs.
