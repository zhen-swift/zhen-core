test on a shared CI runner. Counting comparisons is deterministic and is what the claim
is actually about.

## 2026-10-15 — change 1: the neighbour watch (Claude)

**What landed.** While the ICMP sweep runs, a task re-reads the neighbour table every
`NeighborWatch.interval(targets:)` (25 ms up to 1,024 targets, proportional above — G0 is
why it polls). An address that goes from not-complete to complete during the sweep is this
run's evidence: it is found at that moment as **`neighbor_resolved`** ("resolved during the
scan"), with its MAC, and counts as answered for the sweep's early exit. An entry already
complete when the sweep started is **`neighbor_table`**, now documented as *inherited*.

- `DiscoverySource.neighborResolved`, ranked between `arpReply` and `neighborTable`;
  `answeredThisScan` includes it. Source-breaking for anyone switching exhaustively.
- `NeighborCache.snapshot()` — the table plus its byte size — is a new requirement with a
  default (the entries, size unknown), so existing conformers compile. `DarwinNeighborCache`
  implements it from the sysctl buffer length.
- `SweepState.recordResolution(_:mac:at:)`: a new host → `hostFound` as `neighbor_resolved`;
  a host that already answered → only its MAC is filled in (`hostUpdated`), never a second
  count; an echo after a resolution → `hostUpdated` with `probe_reply` winning. Addresses
  outside the sweep are ignored.
- Every scan artifact now has **`run.neighbor_watch`**: `{enabled, mechanism: "poll",
  poll_interval_millis, polls, largest_dump_bytes, resolved}` — whether change 1 was on and
  what it cost, so the study does not have to infer either.
- **Schema 4.** `ScanReport.schemaVersion` 3 → 4. The argument (in the source comment): the
  value set of `discovered_via` changed meaning — a 3-reader would count every
  `neighbor_resolved` host as unknown, and `neighbor_table` no longer covers resolutions made
  during the scan. `minimumReadableSchema` stays 1; new fields are decoded if present.

**Decisions (all inside the brief).**
1. Polling, not a routing socket — G0.
2. Within one sweep the sources are exclusive: a host is `neighbor_resolved` OR
   `neighbor_table`, never both. Baseline = complete entries at sweep start.
3. A host that resolves between the watch's last poll and the final table read is still
   `neighbor_resolved` — it was not complete at the start — but untimed (`at: nil`); it gets
   no first-contact time in change 3.
4. **`--no-neighbor-watch` (change 7) keeps study 1's behaviour exactly**: no polling, and
   every complete entry found by the final read is `neighbor_table`, as in 0.7.0. That is
   what G3 compares against.

## 2026-10-15 — change 3: first-contact time and its history (Claude)

**Per host.** `HostFacts.firstContact: Duration?` and `firstContactCold: Bool?` (wire
`first_contact_millis`, `first_contact_cold`; cold is nil exactly when the time is). The
sweep sets `firstSentAt` and `cold` at an address's first recorded transmission — cold when
no complete neighbour entry is known *at that moment* (start snapshot plus anything the
watch has seen since) — and the first evidence of any kind stops the clock: the echo's
`receivedAt`, or the watch's poll instant for a resolution. Evidence that predates the
first transmission is not timed. A resolution seen only in the final read is untimed
(change 1, decision 3). `Device` carries the latest run's pair; the composite merge carries
the pair from one engine, never a time from one with the flag of the other.

**History.** `HistoryLedger.Record.firstContactSamples`, newest 32, appended on every fold
that has a time (new and existing records alike), cold and warm both kept — `ReachPlan`
filters to cold. A merge keeps the loser's samples first, then the survivor's, newest 32.
`StoredDevice` exposes them.

**Wire — decision.** Not a key on the device line but a line of its own,
`{"type":"first_contact","first_contact":{"key":…,"first_contact_samples":[{millis,cold}…]}}`,
written after its device line on append and on compaction. The reason is G2's last clause:
0.7.0 decodes a device line and *ignores* unknown keys, so a 0.7.0 compaction (the app is
pinned to 0.7.0 and shares the file) would silently drop a key; a line of unknown *type* it
cannot decode, and 0.7.0 keeps those verbatim and writes them back after its snapshot.
Reload joins samples to records after every line is read, by key, or — for a key a merge
has absorbed — the oldest record that carries it as an identifier.

## 2026-10-15 — change 4: the sweep honours the plan (Claude)

**Where the plan travels:** `ScanTarget.reach: ReachPlan?`, default nil, excluded from
`CodingKeys` (a plan is an input rebuilt per scan; what was used is reported as `run.reach`,
change 6). On the target, not the engine, because it is a fact about this scan of this
network, and change 5's look-longer passes its own.

**What `SweepState` does with it** (`Sources/ZhenDarwin/ICMPSweep.swift`):

- A plan that does not `extendsAnyWait` (`.learned`) is dropped at `init`, so `.learned`
  and no plan take the same code path: the 0.7.0 phase two, unchanged. Gate G3 depends on it.
- An address whose plan wait is non-zero gets the plan's attempt count and a **slot** of
  `wait / attempts`: each gap is one slot, the one before the final transmission is
  scattered by C8's deterministic ±25% factor, and none is shorter than the retransmit
  interval. So the final transmission goes out about one slot before the deadline. Every
  transmission to an ARP-incomplete address is an ARP trigger, so this spreads ARP attempts
  across the wait.
- Its **deadline** is first transmission + plan wait, in a second `ExpiryQueue<IPv4Address>`;
  evidence (an echo or a resolution) cancels it. When it comes due under `.history`, the
  learned tail floors it: if first transmission + tail is still ahead, it is rescheduled
  there. `.fixed` has no floor.
- Extended addresses' transmissions do **not** move `lastTransmissionAt` /
  `lastTightTransmissionAt`, so the network-wide tail is anchored on the learned path alone.

## 2026-10-15 — change 5: look longer (Claude)

`ScanRunner.lookLonger(_ addresses: [IPv4Address], wait: Duration, settings:, progress:)`
(`Sources/ZhenScan/ScanRunner.swift`), returning `CompletedExtension` (its own file). It reads
the latest run; with none it sweeps nothing and says so in a degradation. Otherwise it keeps
the addresses inside that run's network, sweeps only them (`ScanTarget.addresses`) under
`ReachPlan(policy: .fixed(wait))` — so each waits `wait` from its first transmission, with the
attempts that wait earns, spread across it (change 4) — filters the result to the asked
addresses (the sweep's final table read reports table-only hosts anywhere in the network),
builds devices as a run does, and hands them to the new requirement
`HistoryStore.recordExtension(_ devices: [Device], of run: UUID)`.

The rule is in the ledger, `HistoryLedger.foldExtension(_:of:)`, above both stores:

- Only the latest run can be extended; any other id is an empty fold.
- A found device not in that run: its record gets the run's id, an `appeared` ("answered
  again at …", or "joined at …" for a record history never had), its observed fields
  (addresses, MAC, TTL, RTT, sources, first contact, `lastSeen`) and a first-contact sample.
  It keeps what a sweep cannot see: names, ports, fingerprint, vendor.
- A found device the run already had is left exactly as it is.
- Nothing else: no other record, no `disappeared`, `latestRun` unchanged, no reconciliation
  (which can remove a record and is a run's business).
- `LogHistoryStore` writes it like a port scan — device lines and event lines, never a run
  line; `InMemoryHistoryStore` hands it to the ledger in one line.

**Decisions.** (1) The requirement takes devices, not a report — a report is a run. (2)
`ipChanged`/`renamed` are not derived for an extended device; the brief says the only event
is `appeared`. (3) The CLI does not use `ScanRunner` (it has its own pipeline), so
`zhen scan --look-longer` (change 7) calls the same ledger rule through its own path.

carries its own `discovered_via`". Turning `addresses` into objects would do that

device line, and that is acceptable because it is a fact about one run, like
