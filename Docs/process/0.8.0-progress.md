**D8.1 — behaviour preserved, with one ordering change.** ARP and SYN now send due
retransmissions before never-sent probes, earliest first, where they interleaved in
address order. That is the ICMP sweep's existing policy. What is sent and the deadlines it
is armed with are unchanged.

**D8.2 — why a heap and not the timing wheel `02-the-cli.md` cites.** Deadlines here are
continuous instants from adaptive budgets, not ticks, and a wheel needs a resolution
chosen up front. At the sizes that matter (≤ 200k) log n is under 18. The heap is
simpler, and the test pins the bound.

**D8.3 — G8 as a comparison count, not a timing.** A wall-clock benchmark is a flaky
test on a shared CI runner. Counting comparisons is deterministic and is what the claim
is actually about.

## 2026-10-15 — G0: the routing socket says nothing when ARP resolves; change 1 polls (Claude)

entry resolves, to an unprivileged process? **Answer: no.** Change 1 therefore re-reads the
table on a timer, and `run.neighbor_watch.mechanism` says `poll`.

The spike is `Docs/process/0.8.0-spike-route-socket.swift` (args: seconds to listen, the
socket's protocol filter, and an optional address to send an `RTM_GET` for, which proves the
socket is live). Compiled with `swiftc -O` and run as uid 501 / euid 501. The machine was on
10.10.40.0/24 (`en0` 10.10.40.19, gateway .1) — not the study LAN, which does not matter here:

## 2026-10-15 — change 1: the neighbour watch (Claude)

**What landed.** While the ICMP sweep runs, a task re-reads the neighbour table every
`NeighborWatch.interval(targets:)` (25 ms up to 1,024 targets, proportional above — G0 is
why it polls). An address that goes from not-complete to complete during the sweep is this
run's evidence: it is found at that moment as **`neighbor_resolved`** ("resolved during the
scan"), with its MAC, and counts as answered for the sweep's early exit. An entry already
complete when the sweep started is **`neighbor_table`**, now documented as *inherited*.

- `DiscoverySource.neighborResolved`, ranked between `arpReply` and `neighborTable`;
  `answeredThisScan` includes it. Source-breaking for anyone switching exhaustively.
- `NeighborCache.snapshot()` — the table plus its byte size — is a new requirement with a
  default (the entries, size unknown), so existing conformers compile. `DarwinNeighborCache`
  implements it from the sysctl buffer length.
- `SweepState.recordResolution(_:mac:at:)`: a new host → `hostFound` as `neighbor_resolved`;
  a host that already answered → only its MAC is filled in (`hostUpdated`), never a second
  count; an echo after a resolution → `hostUpdated` with `probe_reply` winning. Addresses
  outside the sweep are ignored.
- Every scan artifact now has **`run.neighbor_watch`**: `{enabled, mechanism: "poll",
  poll_interval_millis, polls, largest_dump_bytes, resolved}` — whether change 1 was on and
  what it cost, so the study does not have to infer either.
- **Schema 4.** `ScanReport.schemaVersion` 3 → 4. The argument (in the source comment): the
  value set of `discovered_via` changed meaning — a 3-reader would count every
  `neighbor_resolved` host as unknown, and `neighbor_table` no longer covers resolutions made
  during the scan. `minimumReadableSchema` stays 1; new fields are decoded if present.

**Decisions (all inside the brief).**
1. Polling, not a routing socket — G0.
2. Within one sweep the sources are exclusive: a host is `neighbor_resolved` OR
   `neighbor_table`, never both. Baseline = complete entries at sweep start.
3. A host that resolves between the watch's last poll and the final table read is still
   `neighbor_resolved` — it was not complete at the start — but untimed (`at: nil`); it gets
   no first-contact time in change 3.
4. **`--no-neighbor-watch` (change 7) keeps study 1's behaviour exactly**: no polling, and
   every complete entry found by the final read is `neighbor_table`, as in 0.7.0. That is
   what G3 compares against.

## 2026-10-15 — change 2: `SweepReach` and `ReachPlan` (Claude)

`Sources/ZhenCore/Time/ReachPlan.swift`, portable and pure. `SweepReach` is `.learned`
(study 1's single learned tail), `.history(percentile:)` (default 0.97) or
`.fixed(Duration)`. `ReachSettings` holds every constant of the brief's table, so change 9's
flags can move each one. `ReachPlan.make(addresses:network:devices:policy:settings:now:retention:)`
builds the plan before the sweep; `wait(for:)` is the plan's own number (zero = the learned
tail alone) and `wait(for:learnedTail:)` is what the sweep arms. `StoredDevice` gains
`firstContactSamples` (defaulted in its initialiser, so callers compile); change 3 fills it.

**Decisions (brief silent or ambiguous; each also in the questions file).**
1. **Attempts:** base 3, plus one per *whole* `attemptsStep` beyond the first, capped at 8.
   The first 500 ms is what the base already covers (study 1's default declared absence at
   ~0.4 s with three), so the brief's 1.5 s first-scan wait gets **5** attempts, not 6.
2. **Percentile:** nearest-rank — always a time that was actually observed, and at exactly
   20 samples P97 is the maximum, the conservative reading.
3. **Expected:** a device whose IPv4 address is in this network and in the target, last
   seen inside the retention passed in. The command line passes `.forever`, which makes a
   device last seen a year ago expected. Questions file.
4. **History is per network:** only devices with an address inside the scanned network
   contribute samples — another network's times say nothing about this one.
5. **The floor:** under `.history` the learned tail floors every wait (history only
   lengthens); `.fixed` is exactly what it says.
6. `extendsAnyWait` is false under `.learned` — that is how the sweep (change 4) knows to run
   study 1's schedule unchanged.
