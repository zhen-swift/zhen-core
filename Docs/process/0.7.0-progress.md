## Decisions

### Changes 1 and 2 — ports in history (`ef1d976`)

**D1.1 — the shape.** `HistoryStore.recordPorts(_ result: PortScanResult, targeted: [IPAddress],
at: Timestamp) -> [DerivedEvent]`, a protocol **requirement**, implemented on
`HistoryLedger.foldPorts(_:targeted:at:) -> Fold`. A requirement rather than a defaulted
extension for the reason `setRetention` already gives in `HistoryStore.swift`: a default
would let a conformance silently drop what it is given. `at` is a parameter because the
ledger has no clock, which is what keeps it testable.

**D1.2 — what it writes.** `LogHistoryStore` appends the device lines and the event lines,
and **no run line**, because a run line is what `reload` takes the latest run from.
`PortScanResult` stays non-`Codable`, as frozen. `append(events:run:)` now takes an optional
run. A fold that matched nothing writes nothing (`Fold.updatedRecords`, new, defaulted 0).

**D1.3 — which record an address belongs to.** The one **the latest run saw** at that
address. An absent record's old address is not trusted with what answers there now: a lease
moves, a port answer carries no MAC, and the app guarded this exact case with a MAC
comparison that core cannot make. So the match is refused. Ties between present holders go
to the lowest ordinal, the rule `match` already states.

**D1.4 — the fingerprint travels with the ports.** `PortScanResult.fingerprints` describes
the host the probe reached, so it is folded onto the same record. Not named in the frozen
decision; recorded here because it is the honest translation of the result into a device
line, and dropping it would lose something the engine measured.

**D1.5 — `lastSeen` is not touched.** Strictly "touches presence not at all". `lastSeen` also
decides which observation wins a merge, so moving it from a port scan would change identity
outcomes as a side effect.

**D1.6 — events carry a fresh `runID`.** `DerivedEvent.runID` is non-optional and there is
no run. A fresh UUID names the port scan and matches no `ScanRun` on purpose.

**D2.1 — which transitions are events.** As frozen: only those involving `open`. Kinds are
`portOpened` (anything → open) and `portClosed` (open → anything else; the detail says which
state). The same names and the same rule `ScanEventKind`/`deriveEvents` already used
("Only `.open` transitions are events"), so the two event models agree.

**D2.2 — a first observation is not an event.** "Transition" needs a prior state. A port
never seen before is quiet, open or not — the same reason a first run derives no `appeared`.

**D2.3 — merge, not replace — also in `fold(report)`.** The frozen rule "a port absent from
the new result is not a close" only holds if absence does not erase. `fold` replaced
`device.ports` wholesale, so a run without a port stage forgot every port and the next deep
run would report them all opening. Ports are now merged by (port, protocol, address); a
port at an address the device no longer holds is dropped (leaving it is already the
`ipChanged`). This is a behaviour change for `zhen hosts`/the app: ports from an earlier
deep scan now persist through discovery-only runs. Recorded in `CHANGELOG.md`.

**D2.4 — event sentence.** `"22/tcp open at 10.10.20.5 · was filtered"`, in the shape the
other details have. `open_filtered` is spoken "open or filtered".

**Evidence, shown failing first.**
- Against stubs (`foldPorts` returning an empty fold, `recordPorts` returning `[]`): 12 of
  13 new tests red — every positive behaviour, including all six open-involving cells of
  the 16-pair table. The 13th was strengthened so it failed too (it asserted only the end
  state and passed vacuously).
- The six guard tests pass against a no-op by construction, so each was shown red by
  breaking the one line it guards, then restored:

  | Guard | Break | Red |
  |---|---|---|
  | not a run | `latestRun?.id = UUID()` in `foldPorts` | `touches presence not at all` (2 issues) |
  | unknown host skipped | `presentHolder(of:) ?? records.keys.first` | red only after strengthening the test to check no record gained the ports — the first version checked the count alone and passed |
  | untargeted host | `where asked.contains(address) \|\| true` | `not asked about is not folded` |
  | absent record | drop `lastRunID == current` | `An absent device's address is not trusted` |
  | first sighting | treat a missing prior as `closed` | `A port seen for the first time` + the reopen test |
  | ports at a left address | drop the `holding` filter | `Ports at an address the device no longer holds` |
- 632 → 645 tests, all green.

### Change 9 — MAC history on the ledger's `Record` (`9bfb877`)

**D9.1 — every MAC, not only prior ones.** `Record.macHistory: [MACSighting]` holds every
address including the current one, so the current row has a span too — A3 asks for "a date
range" on every row. `Record.priorMACs` is the frozen name, computed: all but the current.

**D9.2 — the link is the reason.** A3 also asks for "the reason it merged". `MACSighting.Link`
is `original`, `rotation(by: HostIdentifierKind)` — the candidate `resolve` matched on, now
returned alongside the record — or `merge(by:)`, the identifier `nextGroup` grouped on, now
returned with the group. No new identity rule: both values already existed inside the fold
and were discarded.

**D9.3 — it reaches `StoredDevice`.** The app reads `store.devices()`, never a `Record`.
`StoredDevice.macHistory`, defaulted `[]` in the initialiser so existing callers compile.

**D9.4 — seeding an older record.** A line with no `mac_history` (every 0.6.0 line) seeds one
`original` sighting spanning the record's `firstSeen` to the device's `lastSeen`. Honest for
the burned-in MAC most devices have; a rotation before 0.7.0 was never written down and is
not invented. Done in `Record.init` (parameter `macHistory: [MACSighting]? = nil`), so every
construction path — the log, the in-memory store, the app's previews — seeds the same way.

**D9.5 — lenient on read.** An unknown `link` or `by` decodes as `original`. Strict decoding
would fail the whole device line into the unreadable pile, and the device would disappear
from every listing to protect the reason one address joined it.

**Known defect, not fixable here — older readers.** A 0.6.0 build reading a 0.7.0 store
ignores `mac_history` and **drops `portOpened`/`portClosed` event lines** (its `reload` skips
an event whose kind it does not know, rather than preserving it). The next time it rewrites
the file — a merge, a prune — both are erased. The fault is in the old reader; the frozen
decision to use the existing line shapes rules out the one mitigation (a new line *type*,
which 0.6.0 would preserve verbatim). Written into `CHANGELOG.md` as an upgrade warning and
raised as question Q1.

**Evidence.** All 7 tests red against a stub that never recorded a sighting. The leniency
test red when `by` was decoded strictly as `HostIdentifierKind` (the device vanished: count
0). 648 → 656.

### Migration gate — a store 0.6.0 wrote (`b223e6d`)

**DM.1 — a real 0.6.0 file, written by 0.6.0.** `Scripts/make-history-fixture` depends on
zhen-core `exact: "0.6.0"` and drives 0.6.0's own `LogHistoryStore`; every fold, append and
compaction in the fixture is 0.6.0's. The remote tag and the local tag are the same commit
(`ae0fc58`); it was run here against the local repository by `file://` URL, and the committed
manifest names GitHub so anyone can rerun it. Scans are synthetic and the identifiers
invented: a real capture names real devices on JC's network, and this repository is public.

What it stages: a deep scan; a discovery-only run with a move, a rename and a departure; a
return, a new device, a port closing and a MAC rotation; a split record that 0.6.0 then joined
(which made 0.6.0 compact); a foreign line (`"type":"annotation"`) appended before that
compaction so 0.6.0's own preserved-unreadable path carries it; and a deep scan appended
after the snapshot. 24 lines: 5 device lines ×2, 11 events, 2 runs, 1 foreign.

**DM.2 — what the gate asserts.** Read the fixture with plain `JSONSerialization` (not the
decoder under test) for the expected MACs, last ports per MAC, event ids, latest run and
foreign lines. Then: 0.7.0 loads all of it (and seeds each record's MAC history); folds a run
(→ `disappeared` + `portOpened`) and a port scan (→ `portClosed`) over it; compacts
(threshold 1); reopens; every 0.6.0 event id, every device and the foreign line are still
there, and the absent TV keeps its last known ports.

**Shown failing** on two lossy readers, each a one-line break of `reload`:
- drops what it cannot decode → red: compaction erased the foreign line;
- requires `mac_history` → red, 6 issues: no 0.6.0 device loaded at all.

**DM.3 — found by the gate: a merge was logged twice.** The fixture holds the same `merged`
event, same id, twice. `fold` called `reconcile`, which logs its joins, then logged everything
it derived — the joins again. Present in 0.6.0 and on this branch until `b223e6d`. Fixed by
splitting a non-logging `join` out of `reconcile`; test `A merge proved by a run is logged
once` red first (2 ≠ 1). Duplicates already on disk are left alone: deleting events to tidy
history is the wrong direction for this file. The app will have shown merges twice in
Activity; noted for the app ledger.

**DM.4 — 0.7.0 keeps what it half-understands.** 0.6.0 preserved a line that failed to decode
but dropped one that decoded with an unknown event kind or key kind (Q1's mechanism). Both
now go to `unreadable` and are written back verbatim. Two tests, both red against the code
as it was (the line was gone after compaction).

**DM.5 — `ScanReport.schemaVersion` stays 3.** The rule in `ScanReport.swift`: bumped on "any
breaking change to the shapes in `Model/`". `git diff 0.6.0 -- Sources/ZhenCore/Model` is
empty: no `Model/` type changed. What did change is outside the artifact:
- `DerivedEvent.Kind` gained cases. `DerivedEvent` is not `Codable` and not in a
  `ScanReport`; the log writes its kind as a string. The same shape as `merged`, which was
  added after schema 3 without a bump, and correctly.
- `MACSighting` and `Record.macHistory` live in `Persistence/`, on the ledger's record and
  `StoredDevice`, never on `Device` — the frozen decision for change 9 is also what keeps
  this out of the schema.
- `mac_history` is a field of the *log's* device line, whose own `v` is unchanged: the field
  is optional on read and ignored by an older reader, the additive case the "Why `ScanMode`
  did not bump it" passage describes.
- `zhen events --json` and `zhen export` now emit `portOpened`/`portClosed` as `kind` values.
  Neither document carries a schema number, and a new value of an open string field is the
  additive case again.

A bump would cost every schema-3 reader a refusal to decode a document whose every field it
can still read correctly. No bump.

### Change 4 — `zhen-helper` product (`77e559e`)

**Measured before deciding.** `xcodebuild -list` on this package, before the change, already
lists a `zhen-helper` scheme: SwiftPM synthesises an executable product for each executable
target of a *root* package, and Xcode schemes it. The app's project lists only `Zhen`:
Xcode makes no scheme for a remote package's products. So declaring the product adds a
scheme to neither list (identical `-list` output before and after) — the objection the old
manifest comment recorded does not hold, and the comment now says so with the measurement.

**What the product changes.** A synthesised product does not cross the package boundary.
Shown failing first: a scratch dependent (a build-tool plugin depending on
`.product(name: "zhen-helper", package: "zhen-core")`) failed with
`product 'zhen-helper' required by package 'dependent' target 'EmbedHelper' not found in
package 'zhen-core'`; with the product declared it builds.

**K1 — known defect: hiding the scheme in this package's own Xcode menu is unverified.** Three
attempts in a scratch clone: (1) `WorkspaceSettings.xcsettings` with
`IDEWorkspaceSharedSettings_AutocreateContextsIfNeeded = false`; (2) `xcschememanagement.plist`
with `isShown = false` in both `xcshareddata` and `xcuserdata`; (3) `xcodebuild -list -json`
to see visibility. `xcodebuild` lists every scheme whatever its visibility, so nothing here
can show a hidden scheme from the command line, and `.swiftpm/` is git-ignored besides. The
scheme was there before 0.7.0 and still is; the app's list — the one the objection was about —
never had it. Recorded, not fixed.

### Change 5 — port stage for new devices only (`429f141`)

**D5.1 — `PortStage` in core, not in the runner.** `off`, `everyHost`, `newHosts`, with
`targets(among:known:)` as a pure function. "New" is a question about history and must get
the ledger's answer, and core is where it can be unit-tested (`ZhenScan` has no test target).
**D5.2 — "new" = no first-seen from `HistoryStore.firstSeen(for:in:)`.** The ledger's own
resolution, so a MAC rotation recognised by name is not new. First run: everything is new.
**D5.3 — `deepScan: Bool` replaced, not overloaded.** `run(network:budget:ports:progress:)`.
One way to ask; the app's PR adopts it in the same release that breaks `DerivedEvent.Kind`.
**D5.4 — first-seen is asked once, before the port stage** (it was asked after). The port stage
adds ports and a fingerprint, never an identifier, so the answer is identical either side.
**D5.5 — `ScanRunner.probePorts(_:spec:budget:progress:)`** landed in the same commit: change 1's
runner half — probe known addresses, fold through `recordPorts`, no run. What the app needs
to delete `ProbeOnlyStore` and the `[Bool: any ScanEngine]` map.

**Evidence.** 3 of 5 `PortStageTests` red against a stub returning every host; `firstRun`
(which that stub passes) red under an inverted `newHosts` filter. The runner's three lines
of wiring have no test here — no test target, and it builds a real scanner; covered from
the app. 660 → 665.

### Change 6 — bounded helper check (`3198d6b`)

**D6.1 — bounded, not cached.** The cost was per *launch*; an in-process cache does not survive
one, and core must not persist "the helper did not answer" across launches (it would outlive
the stale registration it describes). The composition-time probe gets
`HelperClient.probeTimeout` = **750 ms**; acquisitions during a scan keep
`acquisitionTimeout` = 3 s. Once the probe fails, the privileged engines are not built, so
nothing in that engine waits again.
**D6.2 — why 750 ms.** A live helper answers in milliseconds including launchd's on-demand
spawn; 750 ms is generous for that and a quarter of the old wait. A helper slower than that
costs one engine build the privileged path, recoverably, and the next build asks again.
**D6.3 — testable without a helper.** The two inline timeouts in `HelperClient` became one
`answer(within:otherwise:_:)`; `CaptureSource`'s acquire closure now receives the bound, and
its initialiser is internal so a test can record which bound `probe` passes.

**The live wait could not be reproduced here.** From a test process the stale registration
answers `helperAbsent` in 1.5 ms; the 3.2 s was measured inside the signed app. Shown failing
first against stubs instead: a never-answering request with a 150 ms bound took **3.19 s**
(the same 3.2 s the app measured), and `probe` passed 3 s rather than 0.75 s. 665 → 669.

### Change 7 — in-app Local Network wording (`e38e19b`)

**D7.1 — a case, `appleLocalNetworkInApp`.** Same grant, no sentence about command-line builds
and terminals; it says the app is listed under its own name instead.
**D7.2 — chosen from the running process, in ZhenDarwin.** `ProbePermissionAdvice.apple(bundleURL:)`
→ in-app when the main bundle's extension is `app`; `appleForThisProcess` reads
`Bundle.main.bundleURL`. The sweep (`ICMPSweepEngine.advice` default) and the naming stage
use it, so the app passes nothing new and the CLI's text is byte-identical. A parameter
threaded from the app was the alternative; rejected because whether a process is an app is
a fact about the process, the same way the CLI's Info.plist section is.

**Evidence.** Against stubs (new remedy repeating the old text; chooser always CLI): the
in-app wording test red (2 issues) and the `.app` choice red. The CLI-unchanged tests pass
against both by design. 669 → 673.
