# zhen-core 0.8.0 — questions for JC

Append-only. Each one says what it blocks and what was done instead, so nothing here
stopped the run. Read once, at the end.

## Q1 — "Expected" with `.forever` retention makes a device last seen a year ago expected (change 2)

The brief: an address is expected when "a history device [was] last seen there inside
retention". The command line's store keeps history `.forever`, so on the command line every
address that has ever answered is expected, and waits P97 with more attempts on every scan,
for ever. A phone that left the household in March costs every scan of that network up to
P97 (capped at 5 s) — once, since an expected address that never answers is not retried
beyond its own wait, but on every run.

**Blocks:** nothing. **Instead:** exactly as written — `ReachPlan.make` takes a
`RetentionPolicy`, and the command line passes the store's, which is `.forever`. The early
exit (change 4) means the cost is paid only by scans where something expected is actually
missing. **Your call:** a separate expected-window (e.g. "seen in the last 30 days, or in
the last N runs") would bound it. Study 2 phase 1 can measure how often it matters.

## Q2 — How the attempt count reads "3 + one per extra 500 ms" (change 2)

Implemented as `base + max(0, floor(wait / 500 ms) − 1)`, capped at 8: the first 500 ms is
what the base three already cover, since study 1's default declared absence at ~0.4 s with
three. So the first-scan wait of 1.5 s gets **5**, P97 = 1,034 ms gets **4**, 5 s gets **8**.
The other reading (`3 + floor(wait / 500 ms)`) gives 6, 5 and 8.

**Blocks:** nothing. **Instead:** the first reading. `--expected-attempts-step` moves the
step, so the study can move the curve; the *offset* is not a flag. **Your call** if the
second reading was meant.

## Q3 — Nearest-rank percentile (change 2)

P97 is nearest-rank, so it is always a time that was actually observed and, from 20 to 33
samples, it is the maximum. An interpolated percentile would be a little lower. Chosen as
the conservative reading for a wait whose job is to catch the slowest host. **Blocks:**
nothing.

## Q4 — `caffeinate -w $$` would have ended at once (run)

The run instructions said `caffeinate -dimsu -w $$ &`. In this harness every shell command
runs in its own short-lived shell, so `$$` exits immediately and caffeinate with it. The run
used `caffeinate -dimsu` as a background task of the session instead, stopped at the end.
**Blocks:** nothing.

## Q5 — XNU may send at most one ARP request per second per entry, and give up after five (change 4)

A hypothesis from reading XNU's `in_arp.c`, not measured in this run: `arp_lookup_route`
sends a request only when the entry's `la_asked` is zero or a second has passed since the
last, and after `net.link.ether.inet.maxtries` (5) unanswered requests marks the entry down
for `arpt_down` (20 s), during which sends fail with `EHOSTDOWN`. If so, the attempts the
plan adds are ARP attempts only when they are ≥ 1 s apart: P97 = 1,034 ms with four attempts
asks ARP about twice, not four times. Change 4 spreads the attempts evenly across the wait
for that reason.

**Blocks:** nothing. **Instead:** spread evenly. **Your call / study 2:** a capture during
G4 (`sudo tcpdump -i bridge100 -n arp`) would settle it; if confirmed, the attempts step
(`--expected-attempts-step`) should be ~1 s rather than 500 ms.

## Q5, a correction — its source

"From reading XNU's `in_arp.c`" overstates it: no XNU source was opened during this run.
The behaviour in Q5 is from memory of that file, unverified against the version macOS 26
ships. Treat it as a hypothesis to measure, as Q5 already proposes.

## Q6 — How long `--look-longer` waits (change 7)

The brief gives the flag but not the wait. **Instead:** 10 s per address, twice
`ReachSettings.cap`, overridable with `--reach <duration>` (the only `--reach` form it
accepts). **Blocks:** nothing. **Your call** for the app's Look longer button, which is a
separate brief.

## Q7 — A 0.7.0 compaction drops `run.reach`, so `--look-longer` then has nothing to ask (change 6, 7)

The run line is decoded by 0.7.0 and written back without keys it does not know, so after the
app (pinned to 0.7.0) compacts the shared file, the latest run has no `expected_missing` and
`zhen scan --look-longer` sweeps nothing (it reports an empty extension, not an error). The
next 0.8.0 scan writes a new run line with it. **Blocks:** nothing; it heals on the next
scan. Moving `reach` to a line of its own, as change 3 did for samples, would survive it —
not done, because the run line is the run.

## Q8 — A machine that scans often may never leave the first-scan wait (change 2, 3)

Seen live in G9 on 10.10.40.0/24: every host's entry was still in the ARP cache from the
scan before (macOS keeps them 20 minutes), so every first contact was **warm**, history
gained no cold samples, and every scan stayed a first scan — 1.5 s everywhere, run after run.
The plan reads cold samples only (the brief's rule, and right: warm times measure ICMP
alone). But a person who scans every few minutes keeps the cache warm and pays the
first-scan wait each time, while the scans that would teach the plan never happen.

**Blocks:** nothing; G4/G5 clear the cache, so they measure what was asked. **Your call /
study 2:** e.g. treat a network whose recent scans are all warm as *not* needing the long
wait (a warm cache means the ARP delay the 1.5 s exists to cover is not there), or let the
first-scan wait apply only to addresses with no complete neighbour entry.

## Q9 — An expected ARP-only host with an inherited entry holds the scan to its full wait (change 4)

`.11` on the testbed answers ARP and not echo. Warm, its entry is complete before the sweep
starts, so it is `neighbor_table` — inherited, not this run's evidence (change 1, as the brief
defines it). If history expects it, the early exit waits for evidence that cannot come, and
the scan runs to `.11`'s full wait (P97, ~1 s) every warm scan; the final table read then
reports it present, so it is not in `expected_missing`. Seen in miniature in G9 here: `.15`
behaved the same way and the scan emitted `settling` for it.

**Blocks:** nothing. **Instead:** as the brief defines evidence. **Your call:** counting a
complete inherited entry as enough for the *early exit* (not for `discovered_via`) is a
one-line change in `SweepState` — remove the address from the wait when the baseline
holds it. Not done, because it changes what "evidence" means.

## Q10 — The version is still 0.7.0 (release)

The brief does not say to release, and 0.7.0's release was its own commit with a tag, so
`ZhenVersion.current` and `Sources/zhen/Info.plist` still say 0.7.0 and
`zhen --version` prints `0.7.0 (<commit>)` from this branch. The commit is what tells builds
apart. **Blocks:** nothing. **Your call:** bump in the release commit, before study 2
freezes the binary, so `run.tool.version` reads 0.8.0.

## Q11 — `discovered_via` is per device, so a resolved v4 host can also say `neighbor_table` (change 1)

G9's cold run here: `.15` resolved mid-sweep and is `neighbor_resolved`, but its device reads
`["neighbor_resolved", "neighbor_table"]`. The second tag is not about the v4 address. Its
IPv6 link-local `fe80::aef4:73ff:fe02:36a2` had a 20-hour-old NDP entry, so it is inherited
(`Device(neighbor:seen:answeredEcho:)`), and `Device.fusing` joined it to the v4 device by
MAC, keeping both sources. Both tags are true, each of a different address.

**Blocks:** nothing. **Instead:** left as it is; the union of evidence per device is what
`discovered_via` has always meant. **Your call / study 2:** the analysis should test
`index("neighbor_resolved")`, not `discovered_via == ["neighbor_resolved"]`, and should not
read `neighbor_table` on a dual-stack device as "the v4 entry was inherited". A per-address
source would remove the ambiguity, but it's a schema change.

## Q12 — `--look-longer` takes the latest run's network but not its interface (change 7)

`executeLookLonger` asks on `latest.target`, but the interface comes from `--iface`, or else
from the primary interface. After `zhen scan --iface bridge100`, a bare `zhen scan --look-longer`
asks about `192.168.64.x` through `en0`'s neighbour table. Found while preparing G7; the
script now passes `--iface` (`562b90a`).

**Blocks:** nothing (the script passes it). **Instead:** left as it is: `ScanRun` doesn't
record the interface, and adding it is a schema field. **Your call:** record the interface
name on the run and let look-longer use it, or refuse look-longer when the latest run's
network isn't on the chosen interface.

## Q13 — A powered-off dual-stack host stays present through its NDP entry (G7, testbed)

G7 live: netbed3 was stopped and the ARP cache flushed. The down scan still reported both its
devices, through `fe80::…` entries in the NDP cache (`neighbor_table`, inherited, about 24 h
left), and wrote `ipChanged 192.168.64.8 → fe80::…`. They were never absent, so
`--look-longer` found `.8`/`.9` and had nothing to record. 0.7.0 does the same:
`Device(neighbor:seen:answeredEcho:)` predates this branch.

**Blocks:** G7's "comes back" half, until the script flushes NDP (`g7` now runs `sudo ndp -c`).
**Your call / study 2:** an inherited NDP entry is the weakest evidence there is. Should it
alone keep a device present, and suppress its `disappeared`? The same goes for a phone that
left the house.

## Q14 — ARP flux on the testbed splits history across MACs (G5, testbed)

Each netbed VM has two interfaces on `bridge100`, with `arp_ignore=0` and `arp_announce=0`
(the Linux default, and the state after a reboot). Either NIC answers ARP for either
address, so `.4` and `.5` swap MACs from run to run. History identifies devices by MAC, so
cold samples land under a different device each run. In G5, `history_samples` read 12, 6,
16, 0, 36, 0, 16, 18, 60, 22 after priming, and 7 of 10 runs stayed `first_scan`. One down
scan wrote 15 `ipChanged` events.

**Blocks:** G5, until the testbed is back in its study configuration, which presumably sets
`arp_ignore=1` and `arp_announce=2`. The tooling for that lives in `zhen-study`, which is a
hard stop for agents. **Your call:** whether the plan should also key cold samples by address
(the plan is per address anyway). A multi-homed Linux box on a real LAN does exactly this.

## Q15 — F1 takes the warm hosts off the first-scan wait, but Q8's scan still lasts 1.5 s (fixes, F1)

F1 is implemented as frozen: an address with a complete entry never takes the first-scan
wait. But on Q8's machine the scan's wall clock doesn't move. Its live hosts are warm, so
they collect warm samples and never cold ones. The cold sample set stays under 20 for good.
Every address with no complete entry still takes the 1.5 s wait, and on a /24 those are
the ~240 addresses where nothing lives. The sweep ends at the latest per-address deadline,
so it ends at 1.5 s, every time. Live on 10.10.40.0/24 (this Mac, unprivileged, scratch
history, two scans a minute apart):

```
a {"paths":{"cold":251,"warm":3,"first_scan":251,"learned_tail":3,…},"history_samples":0,"warm_samples":0} discovery 1516 ms
b {"paths":{"cold":239,"warm":15,"first_scan":239,"learned_tail":15,…},"history_samples":12,"warm_samples":2} discovery 1517 ms
```

In b, all 15 warm hosts took the learned tail, as F1 requires. The 239 cold addresses took
1.5 s, as F1 also requires ("No complete neighbour entry: … `firstScanWait` below
`minimumSamples` (today's rule)").

**Blocks:** nothing. `run.reach.paths` now shows it in every artifact. **Instead:** exactly
as frozen. **Your call / study 2:** what would shorten it is a rule for the *unexpected*
cold addresses, which are the dead ones. For example: give the first-scan wait only to
cold addresses history expects, or to every cold address only while history holds fewer
than `minimumSamples` samples of *either* kind. A network with 20 warm samples has been
scanned enough to know which addresses answer. Either is a change to what study 2 measures,
so it isn't made here.

## Q16 — F1's warm percentile and F2's inherited address are the same addresses (fixes, F1 + F2)

F1 gives the warm samples' percentile to an expected address with a complete entry at sweep
start. F2 says an expected address with a complete entry at sweep start already has the
evidence the report accepts, and the scan must not wait for it. Those are the same
addresses. F2 is applied as the later and more specific rule: such an address is
`inherited`. It is asked on the learned schedule, has no deadline, and is never in the
settling list.

Why not keep F1's wait for its transmissions and drop only the deadline: the sweep sends
an extended address's transmissions spread across its wait, and the transmit phase lasts
until the last of them has gone out. A warm percentile above the learned tail (a host slow
to echo, with its entry cached) would then hold the scan for most of that wait anyway.
Then R2's "ends at the learned tail, not at its plan wait" couldn't hold. R2's fixture uses
a warm P97 of 1.2 s for that reason.

**Blocks:** nothing. **Instead:** the warm percentile is computed and reported
(`run.reach.warm_wait_millis`, `warm_samples`), as F1 asks, and no address waits it.
`run.reach.paths.inherited` counts the addresses F2 took. **Your call / study 2:** if
waiting for an echo from a cached, expected host matters (it would turn its
`neighbor_table` into `probe_reply` with an RTT), F2 would have to allow a wait for those
addresses, and the transmit phase would pay for it.

## Q12, a correction — the run already records its interface

Q12 said "`ScanRun` doesn't record the interface, and adding it is a schema field". That
was wrong. `ScanRun.interface` has been on every run since `cb786da` (the 0.7.0 tag): in
the artifact as `run.interface`, and in history's run line, since the store writes the
whole `ScanRun`. The 0.7.0 fixture's run lines carry `"interface":"en0"`. F5 therefore
needed no schema field. `--look-longer` now reads it (progress, F5).
