# zhen-core 0.7.0 — questions for JC

Append-only. Each one says what it blocks and what was done instead, so nothing here
stopped the run. Read once, at the end.

## Q1 — A 0.6.0 build erases port events and MAC history from a 0.7.0 store (change 2, 9)

0.6.0's `LogHistoryStore.reload` decodes an event line with an unknown `kind` and then skips
it — it does not keep it with the unreadable lines — and it ignores `mac_history` on a device
line. The next time 0.6.0 compacts (a merge, a retention prune, the line threshold), both are
gone from disk. Any `zhen` installed from 0.6.0, or the app before it adopts 0.7.0, can do this
to the shared store.

**Blocks:** nothing. **Instead:** the brief froze "the log shapes that already exist", so port
events are event lines with new kinds. `CHANGELOG.md` says not to point 0.6.0 at a store 0.7.0
has written, and 0.7.0 itself now preserves an event kind it does not know (see the migration
gate), so this cannot recur from 0.7.0 forward. **Your call:** if older readers matter, port
events could be a new line *type* (`"type":"port_event"`), which 0.6.0 already preserves
verbatim. That contradicts the frozen shape, so it was not done.

## Q2 — Keep the tag on `9a2310a`: merge with a merge commit (release)

The app's `Package.resolved` pins 0.7.0 at `9a2310a`, the commit tagged here. 0.6.0 was
squash-merged and tagged on the squash commit; repeating that gives 0.7.0 a hash the app does
not pin. **Blocks:** nothing now. **Instead:** both PR bodies say so. Push the tag as it is and
merge with a merge commit, or re-tag on `main` and re-resolve the app (one command, in the
app's verification file).

## Q3 — The `zhen-helper` scheme in this package's own Xcode menu (change 4, K1)

It was there before 0.7.0: SwiftPM synthesises an executable product for a root package's
executable target and Xcode schemes it. Declaring the product changed no scheme list, and the
app's list is just `Zhen`. Hiding it here would mean committing `.swiftpm/xcode/…` scheme
settings, which `.gitignore` excludes, and the effect cannot be checked from the command line.
**Blocks:** nothing. **Instead:** recorded as K1. Your call whether it is worth un-ignoring
`.swiftpm/xcode/xcshareddata`.

## Q4 — `deriveEvents` treats an absent port as closed; the ledger does not

`ScanEvent.swift`'s `deriveEvents(previous:current:…)` compares sets of open ports, so a port
missing from the newer report reads as `portClosed`. The ledger now merges by key and treats an
absent port as not asked about, as the brief froze. Nothing in the app or the CLI's history
path calls `deriveEvents`. **Blocks:** nothing. **Instead:** left as it was; the two agree on
which transitions are events, not on what absence means. Align it, or retire it?

## Q5 — `zhen scan --deep` has no "new devices only"

`PortStage.newHosts` is used by `ScanRunner`, the app's adapter. The CLI's `ScanPipeline` still
takes `--deep` as all-or-nothing. **Blocks:** nothing; not in the brief. A flag such as
`--deep=new` would be a small follow-up.
