# Port scanning in the CLI

Written 2026-09-24. Plan only, nothing built.

## 1. You already have most of it

Before planning anything, what is in the tree today:

| | Where |
|---|---|
| Three-state port model, `open` / `closed` / `filtered` | `Model/Ports.swift` |
| Service identity with evidence provenance, no port-number guessing | `Model/Ports.swift` |
| `PortScanning` protocol, terminal and streaming | `Engines/Engines.swift` |
| Half-open SYN scan, privileged | `ZhenDarwin/SYNScan.swift` |
| TCP connect scan, unprivileged | `ZhenDarwin/TCPConnectScan.swift` |
| Banner grab + TLS certificate reading, layered over either | `BannerProbingPortScan.swift`, `BannerProbe.swift` |
| OS fingerprint layered over that | `FingerprintingPortScan.swift` |
| CLI surface | `zhen scan --deep [--ports 22,80,443]` |

The engine is not the gap. **The gap is that port scanning is a flag on discovery
rather than a capability.**

## 2. What that costs, concretely

`--deep` scans the ports of hosts *this run's discovery found*. Six consequences:

| | |
|---|---|
| **G1** | You cannot scan a host you already know about without re-running discovery |
| **G2** | You cannot scan a host discovery does not find — a firewalled host that answers no ICMP but has 443 open. The model has `filtered` precisely for this and the CLI cannot reach it |
| **G3** | `--ports` parses comma-separated integers only. No `1-1024`, no `top-100`, no exclusion, no protocol prefix |
| **G4** | The default is 36 hand-picked ports. Fine as a default, but it is the *only* set |
| **G5** | **No UDP at all.** `TransportProtocol.udp` exists in the model and nothing in the tree produces it — the artifact promises a dimension the engine cannot fill |
| **G6** | Scan type is chosen for you: SYN if the helper is up, connect if not. You cannot ask for connect scan on purpose |

G6 is not a small thing. Connect scan is not merely the fallback — it is the *permitted*
option on a network where you may open sockets but not forge frames, and it completes a
handshake, so banner grabbing is natural rather than a second connection.

## 3. The shape: `zhen ports` as a first-class subcommand

```
zhen ports <targets> [--ports SPEC] [--udp] [--scan-type syn|connect|auto]
                     [--service-detection] [--deadline D] [--json|--ndjson]
```

`<targets>` accepts what discovery produces and what a person types: an address, a
comma list, a CIDR, `-` for stdin. That makes this work, which is the point of the
whole exercise — *corrected 2026-09-24: this example read `jq -r '.[].ip'` and failed,
because `zhen hosts --json` emits `{"devices": [...]}` rather than a bare array; and
`top-100` is deferred, so the range is used here instead*:

```
zhen hosts --json | jq -r '.devices[].ip' | zhen ports - --ports 1-1024
```

**`scan --deep` stays.** Discovery-then-ports in one pass is the common case and
deprecating it to prove a point would be worse for the user. `ports` is for targets you
already have; `--deep` is for targets you are about to find.

## 4. Port spec grammar

One parser, in `ZhenCore`, tested as a unit — not inline in the command as today.

| Spec | Means |
|---|---|
| `22,80,443` | those three |
| `1-1024` | inclusive range |
| `top-100` | first 100 by our frequency table, see below |
| `common` | today's 36, the default |
| `all` | 1-65535, and requires `--yes` |
| `T:80,U:53` | protocol-qualified |
| `1-1024,!135-139` | exclusion |

`all` across a /24 is 16.7 million probes. The command prints the probe count and the
estimated floor before it starts, and refuses without `--yes`. That instinct is already
in the codebase — `PortSpec.commonServices` says so in its doc comment — it just has no
enforcement.

## 5. `top-N` needs frequency data, and nmap's is not ours to take

*Resolved 2026-09-24, and the resolution is that `top-N` is not built.*

`nmap-services` carries frequency ranks and is distributed under the Nmap Public Source
License. Copying it in is a licensing problem, not a technical one.

The source chosen instead was IANA's registry. **IANA records WHICH ports have a
service assignment and publishes no ranking of any kind**, so it cannot produce a
top-N — and shipping its list under the name `top-100` would be a frequency claim its
source cannot support, which is the same guess-dressed-as-a-fact that `Ports.swift`
refuses when it declines to name a service from a port number.

What it can produce, and what was built, is a SET. Of the 1,023 well-known ports, 682
carry a real assignment and 341 are Unassigned or Reserved:

```
zhen ports 10.10.20.1 --ports iana
...
3 open · 0 closed · 679 filtered
1 host · 682 ports · 694ms
```

`iana` is `1-1023` minus a third of the probes, losing nothing that was ever going to
answer. It is generated by `Scripts/derive-iana-ports.py`, which is the gate this
section asked for — reproducible from a committed script rather than a pasted list, and
verified by regenerating from both a cached copy and a live fetch and diffing.

A real frequency ordering still wants the study data, and that remains open.

## 6. UDP is the hard one, and it breaks a model invariant

Two separate problems.

**It is slow for a reason you cannot engineer away.** An open UDP port usually says
nothing. A closed one sends ICMP port-unreachable — which Linux rate-limits to roughly
one per second. A thousand closed ports on a Linux host is a thousand seconds, and no
amount of concurrency fixes it, because the limit is at the target.

**It does not fit the three-state model.** Silence on TCP means `filtered`. Silence on
UDP means *open or filtered* and the two cannot be separated. `Ports.swift` argues at
length against collapsing states, and adding UDP forces exactly that choice:

| Option | Cost |
|---|---|
| Add `openFiltered` as a fourth state | Honest. Breaks the JSON enum for every existing reader |
| Report silence as `filtered` | Wrong, and wrong in the direction of under-reporting — the failure the file header warns about |
| Only scan UDP ports where a protocol payload gets a real answer | Honest, narrow, and mostly already built |

**Take the third, then the first.** `SSDPProbe` and `NetBIOSProbe` already send real UDP
payloads and parse real answers. Generalise that into a small payload table — DNS 53,
NTP 123, SNMP 161, mDNS 5353, SSDP 1900, NetBIOS 137 — where an answer is unambiguous
and a non-answer is honestly `filtered`. Blind UDP scanning of arbitrary ports waits for
the fourth state and a version bump of the artifact.

## 7. Output

- **JSON and NDJSON:** `PortObservation` already encodes. Nothing new.
- **Text:** `TextRenderer` currently renders a device table and no ports at all. A port
  view is a new renderer — host, port, protocol, state, service, RTT. Build it as a
  `Grid`-shaped table in the same sense as the app work: columns sized by content.
- **Exit codes:** `ExitCodes.swift` exists. Decide deliberately — is "scanned fine, zero
  open ports" a 0? Yes. Only failure to scan is non-zero, same reasoning as the partial
  discovery result exiting 0.

## 8. Stages

| | Work | Done when |
|---|---|---|
| **1** | `PortSpec` parser in `ZhenCore`: ranges, exclusions, `T:`/`U:`, named sets. Unit tested | the grammar table in this document is all covered by tests, including the rejections |
| **2** | `zhen ports` subcommand, TCP only, targets from argv and stdin | G1 and G2 closed — a firewalled host with 443 open is reportable |
| **3** | `--scan-type` explicit, `auto` keeping today's behaviour | G6 closed; forcing `connect` actually uses connect, proven from the wire — *corrected 2026-09-24: this read "with the helper installed", and for the CLI that is not the variable. The command line passes `capture: .directOnly` and never contacts the helper, so the sharper comparison is both scans AS ROOT with only the flag varied* |
| **4** | Frequency table + `top-N`, sourced and labelled | `top-100` is reproducible from a committed derivation script, not a pasted list |
| **5** | Text renderer for ports | readable at 80 columns, no truncated addresses |
| **6** | Probe-count guard and `--yes` | `all` on a /24 refuses without it and prints the count it refused |
| **7** | UDP by payload table, over the existing SSDP/NetBIOS machinery | every UDP result is `open` from a parsed answer or `filtered`; no guessing |

Stages 1-3 are the actual request. 4-7 are what makes it a tool rather than a flag.

## 9. Deliberately out of scope

- Blind UDP scanning of arbitrary ports — waits for the fourth port state
- IPv6 — the whole engine is IPv4 today; port scanning is not where that changes
- Scripting engine, nmap's NSE equivalent — different product
- Idle scan, fragmentation, decoys — evasion is a different project with a different
  ethical surface, and this tool's audience is someone auditing their own network

## 10. Sequence against everything else

Independent of the responsive-layout work — different package, no shared files. It does
collide with **OUI vendor lookup**, which also wants to touch how a device's facts are
assembled and rendered; do that first or after, not in parallel.

Worth noting: stages 1-3 are roughly a week and they are the part with paper value. A
port-scan capability that reaches a host discovery cannot see is a *finding*, not a
feature — study 2 has a dispersion sweep and no port dimension at all, and this is the
cheapest way to give it one.
