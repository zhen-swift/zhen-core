# 13 · Half-open knocks: the SYN scan and fingerprints

![Pip knocks once with a SYN. The door answers SYN-ACK. Pip never finishes the handshake.](figures/13-hero.svg)

::: short
The short version

- A TCP connection opens with a three-step **handshake**: SYN, SYN-ACK, ACK.
- A **SYN scan** sends only the first step and listens: SYN-ACK means open, RST means closed, silence means filtered. It **never finishes** the handshake.
- Zhen builds each SYN **by hand**, from the Ethernet header down, and sends it through the BPF periscope (chapter 11).
- There's no list of probes sent. The sequence number is a **cookie** that names its own probe.
- With BPF, SYN **replaces** the connect scan, and one gentle extra SYN guesses each host's **operating system family**.
:::

::: word
New word: SYN, ACK, RST

TCP packets carry **flags**. **SYN** means "let's talk", **ACK** means "got it", and **RST** means "no, go away". A normal connection goes SYN → SYN-ACK → ACK.
:::

## One knock, three answers

![SYN gets SYN-ACK (open), RST (closed) or nothing (filtered).](figures/13-handshake.svg)

- **SYN-ACK**: open. Zhen never sends the final ACK.
- **RST**: closed. "The host is there and said no."
- **Nothing**: filtered. That "says only that nothing came back in time" (`IPv4Packet.swift:9-11`).
- It isn't stealthy: "every modern stack logs a half-open probe if it is looking". The real win is that the **app on the far side is never involved**: one packet instead of an accept, a read timeout and a close (`IPv4Packet.swift:13-15`).
- It still says **open** when a server's accept queue is full, where `connect` would time out into "filtered" (`SYNScan.swift:17-19`).

::: word
New word: half-open

A connection is **half-open** when the handshake started and never finished. A SYN scan leaves every open port that way, for a moment.
:::

## Our own kernel helps

![The target's SYN-ACK reaches our kernel, which finds no socket on that port and answers RST by itself.](figures/13-rst.svg)

1. Every SYN in a scan leaves from **one local port**, picked at random between 40,000 and 60,000, with **no socket** behind it (`SYNScan.swift:235`).
2. The target's SYN-ACK arrives at our Mac's kernel.
3. The kernel finds no socket on that port and answers **RST** by itself. "That is what closes it, we do not" (`IPv4Packet.swift:17-20`).
4. Why not open a socket there to stop the RST? Then the kernel "would *complete* the handshake on our behalf and the scan would silently become a connect scan" (`IPv4Packet.swift:20-22`).

## A SYN, built byte by byte

![54 bytes: 14 of Ethernet, 20 of IPv4, 20 of TCP, every number written big-endian by hand.](figures/13-frame.svg)

- `IPv4Packet.syn` writes **54 bytes**: 14 Ethernet, 20 IPv4 and 20 TCP (`IPv4Packet.swift:59-66`).
- Every field is **written by index, big-endian**, with no `unsafe` and no assumed alignment (`IPv4Packet.swift:48-51`).
- The target's MAC comes from the **ARP table** (chapter 12). That's next-hop lookup, not discovery, so the engine deliberately **doesn't claim** the neighbour-table capability (`SYNScan.swift:24-37`).
- **Don't Fragment** is set. A 40-byte datagram never needs splitting (`IPv4Packet.swift:128-131`).
- The TCP checksum covers a **pseudo-header** (source, destination, protocol, length) that is never sent. Leave it out and every stack drops the SYN, which "presents as a scan where every port is filtered" (`IPv4Packet.swift:352-358`).
- When reading a reply, the IPv4 header length is **read, never assumed to be 20** (`IPv4Packet.swift:326-328`).
- TCP options are walked carefully, because a bad length byte could **loop forever** or read past the end (`IPv4Packet.swift:231-234`, `:263-265`).

```swift
var pseudo = [UInt8](repeating: 0, count: 12)
write(&pseudo, at: 0, ip: source)
write(&pseudo, at: 4, ip: destination)
pseudo[8] = 0
pseudo[9] = protocolTCP
write(&pseudo, at: 10, u16: UInt16(tcpLength))
```

## The sequence number is a cookie

![Target, port and a per-scan salt are mixed into the sequence number. The reply's ack minus one must match.](figures/13-cookie.svg)

- A SYN carries a 32-bit **sequence number**. The reply's acknowledgement is that number **plus one** (`IPv4Packet.swift:26-27`).
- Zhen makes it a **cookie**: a hash of the target address, the port and a per-scan **salt**. A reply names its own probe, so the scan keeps **no table** (`IPv4Packet.swift:27-29`).
- The salt came from a packet capture. Two runs minutes apart sent **byte-identical** sequence numbers, so a late reply from the first could decide a port in the second (`IPv4Packet.swift:31-34`, `:165-171`).
- The cookie is **never 0** (`IPv4Packet.swift:182-184`).
- It's a hash, so two probes can collide. The reply's source address and port are checked as well (`IPv4Packet.swift:36-38`).

```swift
// Never zero: a zero sequence would make `ack == 1` on the reply, which is also
// what a stack answering a probe we did not send would produce.
return value == 0 ? 0x5EED_5EED : value
```

## SYN or connect?

![With a BPF device: SYN inside banners inside fingerprinting. Without: connect inside banners.](figures/13-choose.svg)

This is **substitution, not composition** (`DarwinScanner.swift:115-172`):

1. If a BPF device opened, **SYN decides every port**. Running connect as well would ask every host twice for one answer.
2. **Banners** (chapter 6) wrap whichever engine ran. A service name needs a finished handshake, so a full connection is opened only to the few open ports.
3. **OS fingerprinting** is added **only with SYN**, because it writes its own SYN.
4. **IPv6 targets** go to connect, because half-open here is IPv4 only (`FamilyRoutedPortScan`, `DarwinScanner.swift:166-172`).
5. `--scan-type syn` with no device is **refused**, not quietly downgraded. "A flag that says 'use SYN' and silently runs connect is worse than no flag" (`DarwinScanner.swift:131-134`).

```swift
let verdicts: any PortScanning = useSYN
    ? SYNScanEngine(concurrency: effective, budgets: budgets, capture: source)
    : TCPConnectScanEngine(concurrency: effective)
let named = BannerProbingPortScan(base: verdicts)
```

## Which stack are you?

![Sixteen odd probes can crash a doorbell. Zhen sends one polite SYN and reads the order of the options that come back.](figures/13-fingerprint.svg)

- Zhen doesn't do it nmap's way. nmap sends **16 probes**, some deliberately malformed, and several of them crash small devices. "A scanner whose default reboots a doorbell is not a scanner anyone should run." (`OSFingerprintProbe.swift:15-22`)
- Zhen sends **one legal SYN** per host, to a port the scan already found open, offering the common options: MSS, SACK, timestamps and window scale (`OSFingerprintProbe.swift:24-26`, `IPv4Packet.swift:195-212`).
- It needs an **open** port, because a closed port's RST carries no options to read (`OSFingerprintProbe.swift:28-33`).
- It reads the SYN-ACK: TTL, Don't Fragment, window size, and **which options came back, in what order** (`IPv4Packet.swift:236-237`).
- It matches against a **small table** of families: Linux, macOS or iOS, Windows, embedded, network gear. It never guesses a version (`OSFingerprint.swift:199-237`).
- No match gives **"unmatched"**, with everything it saw kept so you can judge (`OSFingerprintProbe.swift:24-26`).
- All hosts share one wait, **1.5 s** by default (`OSFingerprintProbe.swift:60`).

::: word
New word: stack fingerprint

Every operating system's TCP code answers a SYN slightly differently. A **stack fingerprint** reads those habits (option order, window size, starting TTL) to guess the family. It's a guess, so Zhen keeps the evidence next to it.
:::

::: iphone
📱 On iPhone & iPad

- ❌ **No SYN scan.** Writing a raw SYN needs BPF (chapter 11).
- ❌ **No OS fingerprint**, for the same reason.
- ✅ The iPad uses the **connect scan** with banners from chapter 6 (`DarwinScanner.swift:213-215`).
- ❌ `--scan-type syn` is refused with its own sentence: "iPadOS has none" (`DarwinScanner.swift:207-212`).
:::

::: gotcha
⚠️ Gotchas the code remembers

- **Opening a socket on the source port.** The scan silently becomes a connect scan.
- **Leaving out the pseudo-header.** Every port comes back "filtered".
- **Assuming a 20-byte IP header.** The port gets read out of the middle of an option.
- **No salt.** A late reply from the last scan decides a port in this one.
- **Option length 0 or 1.** The option walk loops forever.
- **Matching on window scale.** At first every real host came back "unmatched". The scale follows a device's memory, not its OS, so now it only lowers confidence (`OSFingerprint.swift:245-251`).
:::

::: remember
🧠 Remember

- SYN-ACK means open, RST closed, silence filtered. Never finish the handshake.
- Build every byte yourself, big-endian, with the pseudo-header in the checksum, and let the cookie keep the books.
- With BPF, SYN replaces connect and adds one polite fingerprint. Without it, connect does the job.
:::
