# 11 · BPF: a periscope on the wire

![The periscope pokes out of the castle onto the wire, asks "who has 10.10.20.7?", and the owner answers.](figures/11-hero.svg)

::: short
The short version

- **BPF** is a device, `/dev/bpf0`, `/dev/bpf1` and so on, that lets a program **send and read whole Ethernet frames**. Opening one needs root.
- Zhen uses it for **ARP**. Every host on your network *must* answer an ARP request for its own address, firewall or not.
- Getting a BPF device ready takes **ten settings in a fixed order**.
- One `read()` returns **many packets** packed together. A two-byte mistake in walking them once hid nine hosts.
- A tiny **filter program** runs inside the kernel, so Zhen only gets the frames it asked for.
:::

::: word
New word: BPF

**BPF** (Berkeley Packet Filter) is the kernel's packet periscope. Open `/dev/bpfN`, point it at an interface, and you can read every frame that passes and write frames of your own. In the drawings it's the blue periscope.
:::

**Why bother? ARP.** A ping (chapter 5) can be ignored. ARP can't.

- A host that won't answer ARP for its own address can't receive any frame at all, so no network stack refuses (`ARPFrame.swift:5-9`).
- That's why `sudo nmap -sn` finds hosts an unprivileged sweep misses. In the study, privileged nmap found all ten test hosts, including one that ignores ping (`BPFSweep.swift:14-21`).
- Zhen's ARP engine is `BPFDiscoveryEngine` (`BPFSweep.swift:55`). It runs **next to** the ping sweep, not instead of it, so root never finds fewer hosts (`DarwinScanner.swift:174-190`).

::: word
New word: ARP and MAC address

A **MAC address** is a network card's hardware address, like `3c:22:fb:12:34:56`. **ARP** (Address Resolution Protocol) turns an IP address into a MAC. It shouts "who has 10.10.20.7?" to the whole network, and the owner answers "me, at 3c:22:fb:…".
:::

## A little C file, because of one macro

![Swift can't see BIOCSETIF. A tiny C file computes it and hands Swift the number.](figures/11-shim.svg)

- You change BPF settings with `ioctl(ticket, REQUEST, &value)`. The REQUEST numbers, like `BIOCSETIF`, are C macros: `_IOW('B', 108, struct ifreq)`.
- `_IOW` builds the number from `sizeof(struct ifreq)`. Swift's C importer won't do that arithmetic, so `BIOCSETIF` just **doesn't exist** in Swift (`CBPFShim.h:3-11`).
- The fix is a header, `CBPFShim.h`, holding about a dozen one-line C functions that **return the numbers**. The C compiler does the math for the SDK being built.
- "**This wraps no syscall.** Every function below returns a number." (`CBPFShim.h:13-16`) Swift calls `ioctl`, `read` and `write` itself. The spec says it outright: "Do not wrap `ioctl` itself" (`SPEC.md:146-149`).
- The same header uses `offsetof` to find the fields of each record's header, so nobody has to remember them (`CBPFShim.h:18-26`).
- It's fenced with `TARGET_OS_OSX`. iOS defines `__APPLE__` too, but its SDK has no `<net/bpf.h>` (`CBPFShim.h:32-38`).
- `shim.c` is **empty on purpose**: SwiftPM insists that a C target has at least one source file (`shim.c:1-7`, `Package.swift:109-120`).

```c
/// `BIOCSETIF` — bind the device to an interface, by name in a `struct ifreq`.
static inline unsigned long ns_bpf_setif(void) { return BIOCSETIF; }
```

[`CBPFShim.h:52-53` @ 0.9.0]{.src}

::: word
New word: `ioctl`

**`ioctl`** ("I/O control") is the catch-all door for device settings: "on ticket 5, set option X to Y". Each option is a request number, such as `BIOCSETIF` or `BIOCIMMEDIATE`.
:::

## Finding a free periscope

![Zhen tries bpf0, bpf1, bpf2… and takes the first free one. "Not allowed" stops the search at once.](figures/11-walk.svg)

1. Try `open("/dev/bpf0", O_RDWR)`, then `bpf1`, `bpf2`, up to `bpf255` (`BPFAcquisition.swift:135-173`).
2. **`EBUSY`**: taken. Each device has one owner at a time, and Wireshark, tcpdump, a VPN client or Little Snitch may hold one (`BPFAcquisition.swift:74-79`). Try the next.
3. **`EACCES`** or **`EPERM`**: not allowed. **Stop right away.** Every node has the same owner, so 255 more tries would only say no more slowly (`BPFAcquisition.swift:131-134`).
4. **`ENOENT`**: no more nodes. macOS creates them on demand, so 256 is a ceiling, not a count (`BPFDevice.swift:65-70`).
5. Nothing free means `allDevicesBusy`. A free one gets configured (next section).

```swift
switch errno {
case EACCES, EPERM:
    throw BPFUnavailable.notPrivileged
case EBUSY:
    busy += 1
    continue
case ENOENT:
    break
```

[`BPFAcquisition.swift:146-153` @ 0.9.0]{.src}

## Ten knobs, in this order

![Ten settings, one fixed order. The filter goes last. Promiscuous mode is never used.](figures/11-setup.svg)

The order isn't written down anywhere obvious. "Every line of it was found by a device that silently delivered nothing" (`BPFAcquisition.swift:12-13`). The sequence is `configure()`, at `BPFAcquisition.swift:178-224`.

1. **`BIOCSBLEN`**: ask for a 256 KiB buffer, **before** binding. Asked afterwards, the kernel refuses with `EINVAL` (`BPFAcquisition.swift:18-19`).
2. **`BIOCSETIF`**: bind to an interface such as `en0`, by name, in a `struct ifreq` (`BPFAcquisition.swift:231-251`).
3. **`BIOCGBLEN`**: read the size the kernel actually granted. **Every read must be exactly that size.** A smaller one fails with `EINVAL` every time (`BPFDevice.swift:80-82`).
4. **`BIOCGDLT`**: must say `DLT_EN10MB`, Ethernet. Anything else and Zhen's frames would be nonsense (`BPFAcquisition.swift:191-197`).
5. **`BIOCIMMEDIATE = 1`**: hand over each packet as it arrives. Without it, replies wait for the buffer to fill, "which on a quiet segment is never" (`CBPFShim.h:54-57`).
6. **`BIOCSHDRCMPLT = 1`**: Zhen writes the whole Ethernet header, its own MAC included, so the kernel mustn't touch it (`CBPFShim.h:62-64`).
7. **`BIOCSSEESENT = 0`**: don't read back our own requests. This one's best effort; if it fails, the scan goes on (`BPFAcquisition.swift:209-212`).
8. **`BIOCSETF`**: install the filter, **last**, so nothing arrives unfiltered. The kernel copies the program, so Swift's array only has to live for the call (`BPFAcquisition.swift:261-263`).
9. **`BIOCFLUSH`**: throw away anything caught during setup (`BPFAcquisition.swift:216-218`).
10. **`fcntl(O_NONBLOCK)`**: never block (chapter 4).

**Never promiscuous.** `BIOCPROMISC` is in the shim and nothing calls it. An ARP reply to our request is sent to **our** MAC anyway (`CBPFShim.h:71-74`).

::: word
New word: promiscuous mode

Normally a network card keeps only frames addressed to it. In **promiscuous mode** it keeps everyone's. Zhen never turns it on.
:::

## One read, many packets

![One read() returns a row of records: header, packet, padding. The next record starts at the next 4-byte boundary.](figures/11-records.svg)

- A BPF `read()` returns a **row of records**: a small header (`bpf_hdr`), the packet's bytes, then padding up to a 4-byte boundary (`BPFBuffer.swift:3-11`).
- Step to the next record with **`BPF_WORDALIGN(hdrlen + caplen)`**. Forget the rounding and the cursor lands 1–3 bytes early; every later "packet" is garbage, such as ARP replies from addresses that don't exist (`BPFBuffer.swift:6-10`).
- The header's fields come from `offsetof`. On macOS 26.5 the timestamp is at 0, `caplen` at 8, `datalen` at 12 and `hdrlen` at 16, and `sizeof` is 20 (`CBPFShim.h:24-26`).
- The header's numbers are in **the Mac's own byte order**. The packet after it is in **wire order**, big-endian. Don't copy one into the other (`BPFBuffer.swift:35-38`, chapter 3).
- A short or broken record **ends the walk** instead of failing it. Everything before it still counts (`BPFBuffer.swift:81-90`).

```swift
let step = Int(ns_bpf_wordalign(UInt(headerLength + captured)))
// Zero would loop forever, and a step that does not clear the header we
// just read means the alignment arithmetic disagrees with the kernel's.
guard step >= headerLength, step > 0 else { break }
offset += step
```

[`BPFBuffer.swift:116-120` @ 0.9.0]{.src}

**Who holds the periscope.** It's `BPFDevice`:

- An **actor** with its own thread. The ticket never leaves it; only frames go in and out (`BPFDevice.swift:50-63`).
- **Reading:** a `DispatchSource` wakes up when data arrives (chapter 4). The handler **reads until the device is empty**, because one wake-up can carry one record or two hundred (`BPFDevice.swift:220-233`).
- **Writing:** one `write()` per frame. `ENOBUFS` "means 'not yet', not 'no'", so it retries up to 8 times with a tiny `sched_yield()` pause (`BPFDevice.swift:284-305`).
- **Checking:** `probe()` really opens a device and closes it again (`BPFDevice.swift:177-189`). "Asking whether we are root answers the wrong question… `open()` is the only honest test" (`BPFDevice.swift:6-11`).

## The bug that hid nine hosts

![bpf_hdr's fields end at byte 18, but the struct is padded to 20. Checking against sizeof threw away every read.](figures/11-bug.svg)

1. `struct bpf_hdr`'s fields end at byte **18**. The compiler pads the struct to **20**.
2. The kernel writes the real header length, **18**, into `bh_hdrlen` on every record (`CBPFShim.h:114-122`).
3. An earlier version required `bh_hdrlen >= sizeof(struct bpf_hdr)`. That's `18 >= 20`, so it rejected the first record of every read.
4. The result: "the sweep sent 759 ARP requests, nine hosts answered, and it reported an empty segment." Nothing threw (`BPFBuffer.swift:25-33`).
5. The fix: the minimum is **where the last field ends**, not the struct's size.

```c
static inline size_t ns_bpf_hdr_min_length(void) {
    return offsetof(struct bpf_hdr, bh_hdrlen) + sizeof(u_short);
}
```

[`CBPFShim.h:126-128` @ 0.9.0]{.src}

- It was found by capturing packets next to a live run, "the only thing that could have found it" (`BPFBuffer.swift:32-33`).
- The tests now write **18** on purpose. Writing 20 is what let the bug pass every test (`BPFTests.swift:53-57`).
- These BPF test buffers are **hand-built on purpose**, because the broken cases they test never come out of a healthy kernel (`BPFTests.swift:19-29`). Chapter 12 does the opposite.

## A tiny computer inside the kernel

![The ARP filter: load the frame's type, compare it with 0x806, keep or drop. It runs on every frame.](figures/11-filter.svg)

- A BPF filter is a **little program** the kernel runs on every frame before copying anything to you. It has an accumulator, an index register, and instructions to load, jump and return.
- "Return N" means "keep the first N bytes". "Return 0" means drop.
- Zhen writes its programs **by hand**, as arrays of instructions, with no libpcap. Each one was checked against `tcpdump -d` (`BPFFilter.swift:9-14`).
- "The filter is not an optimisation, it is the difference between reading the replies we asked for and reading the network." (`BPFFilter.swift:5-7`)

```swift
static func arp() -> [bpf_insn] {
    [
        bpf_insn(code: loadHalfwordAbsolute, jt: 0, jf: 0, k: ethertypeOffset),
        bpf_insn(code: jumpIfEqual, jt: 0, jf: 1, k: UInt32(ARPFrame.ethertype)),
        bpf_insn(code: returnConstant, jt: 0, jf: 0, k: acceptWholeFrame),
        bpf_insn(code: returnConstant, jt: 0, jf: 0, k: 0),
    ]
}
```

[`BPFFilter.swift:67-74` @ 0.9.0]{.src}

That's `ldh [12]; jeq #0x806; ret #262144; ret #0`. The SYN scan's filter (chapter 13) is longer:

- **11 instructions**, keeping TCP frames sent to one port (`BPFFilter.swift:109-127`).
- It can't read the port at a fixed spot, because an IP header isn't always 20 bytes. `BPF_MSH` loads "4 × the header-length nibble" into the index register (`BPFFilter.swift:18-23`).
- Its first version had **two bugs** (`BPFFilter.swift:84-97`):
  - `jf` was treated as an index, but it's a **count of instructions to skip**. Every rejected frame fell through to "keep".
  - It had **no fragment check**. A later IP fragment has no TCP header, so the "port" was really payload.

::: iphone
📱 On iPhone & iPad

- ❌ **No BPF at all.** The iOS SDK has no `<net/bpf.h>` and the device has no `/dev/bpf*`. Every BPF file in Zhen sits inside `#if os(macOS)` (for example `BPFDevice.swift:39-41`), and the C shim compiles to an empty file (`CBPFShim.h:32-33`).
- ❌ **No ARP sweep**, so a host that ignores ping and answers only ARP stays invisible on an iPad.
- ✅ The iPad runs what the Mac falls back to: the ping sweep (chapter 5) and the connect scan (chapter 6). It doesn't warn about it, because that's the platform's normal state (`DarwinScanner.swift:193-218`).
:::

::: gotcha
⚠️ Gotchas the code remembers

- **Wrong order.** Setting the buffer size after binding, or reading into a smaller buffer, gives `EINVAL`, which looks exactly like "nothing on this network" (`BPFAcquisition.swift:18-22`).
- **No `BIOCIMMEDIATE`.** Replies wait for the buffer to fill. On a quiet network that's never.
- **Forgetting the padding** between records gives garbage that looks real.
- **`sizeof` versus `bh_hdrlen`.** 759 asked, 9 answered, 0 reported.
- **Tagged networks.** The ARP filter matches untagged frames only. An 802.1Q tag moves the type from byte 12 to 16, and the sweep hears nothing (`BPFFilter.swift:64-66`).
:::

::: remember
🧠 Remember

- BPF is raw frames in and out. Opening it needs root, and Zhen finds out **by trying**, not by asking.
- Ten settings in one fixed order, and the filter goes last.
- One read, many records: step with `BPF_WORDALIGN`, and trust `bh_hdrlen`, not `sizeof`.
:::
