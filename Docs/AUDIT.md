# Documentation and maintainability audit

> **Note, 2026-10-03.** This audit measured the monorepo, `InfinityCastle`, before it was
> split into `zhen-core`, `zhen-app` and `zhen-study`. It names paths as they were there —
> the app's scripts and `Docs/process/` are not in this repository — and is kept unedited
> as the record of that measurement. `Scripts/check-docs.sh` does not check it, for the
> same reason it does not check a ledger.

Run 2026-09-30 against `f7f1f58`. Three questions: does it **run** easily, is it
**understood** easily, is it **maintained** easily. Every finding below is measured, with
the command or file that produced it. Nothing here is a matter of taste.

**Headline: the code is in better shape than the documentation, and the gap has already
cost a real person real time.** On 2026-09-30 the author of this project typed
`zhen scan 10.10.20.11 22` and got an error, because the README's usage section shows only
`zhen scan` and has never mentioned the `ports` command that answers exactly that question.
That is finding R1, and it is not hypothetical.

---

## 1. Does it run easily?

| | Finding | Severity |
|---|---|---|
| **R1** | **The README documents 1 of 6 subcommands.** `zhen ports`, `hosts`, `events`, `history` and `export` appear nowhere in it. Neither do `--check`, `--udp`, `--scan-type`, `--ports-view`, or IPv6 targets | **high** |
| **R2** | **The README's build instructions are wrong and cannot work.** It lists three `cd … && swift build` lines; two are now the identical `cd zhen` (they were `zhen-core` and `zhen-cli` before the packages merged) and the third is `cd zhen-app`, which no longer has a `Package.swift` at all. A reader following it gets a duplicate step and then an error | **high** |
| **R3** | **`Scripts/install.sh` is not mentioned in the README.** The supported way to install the tool is undocumented; the README shows only `swift build` | **high** |
| **R4** | The man page is complete and checked — `Scripts/check-manpage.sh` verifies all 6 subcommands and 36 options in both directions. **But nothing tells a reader the man page exists**, and it is only present if they ran `install.sh`, which R3 hides | medium |
| **R5** | First-run without the privileged helper works and explains itself in a degradation. Verified in the CLI-v1 report. **Not written down anywhere a user reads**, so "why is this slower / finding less than nmap" has no answer outside the source | medium |

R2 is self-inflicted and recent: the path rewrite during the reorganisation substituted
folder names inside that code block without noticing it had collapsed two distinct
commands into one and broken the third.

## 2. Is it understood easily?

| | Finding | Severity |
|---|---|---|
| **U1** | **`Docs/` holds 31 files and 9,700 lines; 15 of the 30 non-index files are absent from the index.** The index opens "Written to be read in order. Each document assumes the ones above it", which is now false for half the folder | **high** |
| **U2** | **Roughly 4,900 of those 9,700 lines are process exhaust, not documentation** — three progress ledgers (2,739 lines alone), three run reports, six agent prompts, four plans, one questions file. All were correct to write; none of them is what a newcomer needs, and nothing separates them from the four documents that are | **high** |
| **U3** | The index carries two stale claims of its own: it says the project is "three packages under `zhen`" (it is one package plus an Xcode project) and describes the privileged helper as "not built yet" (it is built, installed, and proven from the wire) | medium |
| **U4** | `03-zhen-app.md` (350 lines) describes the app as a SwiftPM package with `.defaultIsolation` in its manifest. The app has been an Xcode target since `b67babf`. The isolation *reasoning* still holds; the mechanism it names is gone | medium |
| **U5** | There is **no document that tells a user how to use the tool**. The man page is a reference, not a manual: it lists flags and does not show a task | **high** |

The count in U2 is the finding, not a complaint about any one file. A progress ledger is
the right artifact for an unattended agent run and a bad first thing for a human to open.

## 3. Is it maintained easily?

Better than the two sections above. What is in place, measured:

| | In place |
|---|---|
| Tests | 627 across 138 suites, green on macOS at `c2fabdc` |
| CI | Path-filtered: a CLI change runs the tool jobs, an app change runs the app job, a library change runs all. Verified by classifying real commits |
| Linux portability | Enforced on every change, not asserted — `ZhenCore` builds and its tests run in CI |
| The Xcode project | Generated by one script, byte-identical on regeneration, and adding a view file does not change it (synchronized root groups) |
| Fixed-size ratchet | `Scripts/check-fixed-sizes.sh` fails if the count rises |
| Man page | `Scripts/check-manpage.sh`, both directions, and it **refuses to report a result it could not measure** |
| Identifier drift | `Scripts/verify-identifiers.sh` reads the authoritative value from the code |

| | Finding | Severity |
|---|---|---|
| **M1** | **No check catches documentation drift.** Every mechanism above guards code or generated artifacts. R2, U3 and U4 are all documents asserting a structure the repository no longer has, and each survived because nothing looks | **high** |
| **M2** | Five `zhenTests` fail on Linux — four need a scanning engine, one assumes a non-root runner. Known and recorded, but the Linux job is red, and a permanently red job stops being read | medium |
| **M3** | `Scripts/release.sh` has never been run against Apple. Notarization is untested, which means the first person to try it debugs it | medium |
| **M4** | `_to_delete/` and `.locks-stale/` are committed leftovers from a session that could not unlink files | low |

## What to do, in order

1. **Fix the README's Building, Using and install sections** (R1, R2, R3). Highest value
   per line in the repository — it is the first thing anyone reads and it is wrong.
2. **Write the manual** (U5) — one document, task-shaped, covering every subcommand. This
   audit ships with `Docs/MANUAL.md`, which is that document.
3. **Split `Docs/` by audience** (U1, U2). Reference and briefs stay; ledgers, reports,
   prompts and plans move under `Docs/process/` with the index saying plainly that nothing
   in there is documentation. One `git mv` and an index rewrite.
4. **Add a documentation check** (M1). The cheapest useful version: assert that every path
   and command named in `README.md`, `CONTRIBUTING.md` and `Docs/README.md` exists — the
   same shape as `verify-identifiers.sh`, which caught a true positive on its first run.
   R2 would have been caught the day it was introduced.
5. Correct U3 and U4 in place, and delete the stale mechanism claims rather than the
   reasoning around them.
6. M2, M3, M4 belong to the Linux phase, the release phase, and one `rm -rf`.

## What is deliberately not a finding

- The SPEC's out-of-date parts. They are marked, dated, and amended in place — a
  specification that records being overtaken is more useful than one quietly rewritten.
- The briefs addressing the reader directly. `CONTRIBUTING.md` explains why, and the
  reasoning in them is the record of why each layer looks as it does.
- Comment density. 40–45% in the large files, and the comments say *why*. That is an asset
  and the most common way to damage a codebase like this is to "clean it up".
